# :bookmark_tabs: Лабораторна робота №2
## Тема: "Проєктування та розроблення кастомних віджетів візуальної складової мобільного застосунку"

### 1. Мета роботи
Поглиблення знань архітектури Flutter, опанування принципів декомпозиції користувацького інтерфейсу, створення перевикористовуваних (reusable) UI-компонентів, реалізація навігації між екранами та забезпечення адаптивності дизайну без прив'язки до бізнес-логіки.

---

### 2. Завдання до лабораторної роботи

**Мета завдання:** Розробити візуальну складову мобільного застосунку (UI-шар) на основі обраної тематики (IoT), імплементувати систему навігації та забезпечити масштабованість кодової бази через інкапсуляцію віджетів.

**Функціональні вимоги:**
1. **Екранна база:** Реалізація мінімум 4-х незалежних екранів (Screens):
   - Екран авторизації (`LoginScreen`).
   - Екран реєстрації (`RegistrationScreen`).
   - Профіль користувача (`UserProfileScreen`).
   - Головний екран (`MainScreen` або `Dashboard`), який візуалізує основну ідею вашого IoT-застосунку.
2. **Маршрутизація (Routing):** Налаштування зв'язків між екранами з використанням навігаційного стека Flutter (наприклад, `Navigator.push`, `Navigator.pop` або іменовані маршрути).
3. **Mock-дані:** Оскільки імплементація бізнес-логіки не вимагається, всі дані на екранах мають бути статичними (заглушками), але візуально відповідати реальному контенту.

**Критерії приймання (Acceptance Criteria) та архітектурні обмеження:**
- **Адаптивність (Responsive Layout):** Інтерфейс не повинен мати "переповнень" (Overflows). Застосунок має коректно рендеритися та масштабуватися на екранах різних розмірів — від iPhone 8 (ширина ~375dp) до стандартного планшета. Вимагається застосування `MediaQuery`, `Expanded`, `Flexible` або `LayoutBuilder`.
- **Декомпозиція UI (Reusability):** Суворо забороняється дублювання коду. Повторювані елементи (наприклад, кастомні кнопки, текстові поля, картки пристроїв) мають бути винесені в окремі Stateless/Stateful віджети та приймати параметри через конструктор.
- **Обмеження об'єму файлів (Clean Code):** Розмір одного файлу з віджетом **не повинен перевищувати ~160 рядків коду** (оптимально — до 120). Перевищення цього ліміту сигналізує про недостатню декомпозицію і вимагає розділення файлу.
- **Дизайн-система:** Допускається лаконічний ("квадратіш практіш") дизайн, проте вимагається консистентність: єдина кольорова палітра, стандартні відступи (padding/margin), уніфіковані шрифти та форми.

### 3. Порядок виконання

#### 3.1. Синхронізація репозиторію
1. Успішний захист [Лабораторної роботи №1](https://github.com/Berezhnyj/mobile-app-development-labs/tree/lab-01) є блокером для здачі цієї роботи.
2. Переконатися, що гілка з Лабораторною роботою №1 успішно змерджена у `main` (або `master`).
3. Створити нову гілку (наприклад, `feature/lab-2-ui`) від актуального стану `main`.

#### 3.2. Розробка UI та навігації
1. Створити директорію `lib/screens/` для зберігання файлів сторінок.
2. Створити директорію `lib/widgets/` для зберігання кастомних перевикористовуваних компонентів.
3. Імплементувати візуальну складову згідно з вимогами.
4. Налаштувати переходи між екранами.

#### 3.3. Статичний аналіз та аудит
1. Переконатися у відсутності помилок лінтера (аналізатор налаштовано в Лаб. №1).
2. Провести тестування інтерфейсу на різних конфігураціях емуляторів (телефон, планшет) для перевірки адаптивності.

### 4. Вимоги до звітності

1. **Pull Request:**
   - Створити PR із гілки виконання (наприклад, `feature/lab-2-ui`) у `main`.
   - В описі PR детально перелічити реалізовані екрани та основні кастомні віджети.
   - У коментарі до PR зазначити: ПІБ студента.
2. **Медіа-докази:**
   - Обов'язково додати до PR відео (або GIF) з демонстрацією навігації та роботи застосунку.
   - Додати скріншоти (бажано на двох різних розмірах екрана — телефоні та планшеті).
3. **Документація:** Оновити документ з лабораторними, додавши посилання на PR: [GDrive](https://docs.google.com/spreadsheets/d/1IzZOFue29ZzfdJpzS1i3OjQFC5o94-pVFRUsPHmXqIQ/edit?usp=sharing).

### 5. Критерії оцінювання

| Критерій | Вага |
|----------|------|
| Наявність 4+ екранів та налаштована навігація | 25% |
| Глибина декомпозиції (створення reusable віджетів) | 25% |
| Респонсивність (коректне відображення на різних розмірах, відсутність overflow) | 20% |
| Дотримання архітектурних лімітів (<160 рядків на файл) та чистота коду | 15% |
| Оформлення звітності (PR, відео/скріншоти, проходження CI/CD) | 15% |

### 6. Вимоги до захисту (Контрольні питання)

Для успішного захисту лабораторної роботи студент повинен бути готовим:
1. **Теорія:**
   - Пояснити різницю між типами роутингу у Flutter (Navigator 1.0 vs Navigator 2.0 / Router).
   - Пояснити призначення `MediaQuery` та як працює механізм побудови респонсивного UI.
   - Назвати базові віджети Flutter (Container, Column, Row, Stack тощо) та пояснити їхні ключові властивості (properties).
2. **Практика (Live Coding):**
   - У режимі реального часу, за вимогою викладача, створити новий простий компонент або модифікувати існуючий у вашому коді.

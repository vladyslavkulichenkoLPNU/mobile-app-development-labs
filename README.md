# :bookmark_tabs: Лабораторна робота №3
## Тема: "Реалізація базової бізнес-логіки та функціональних інтерфейсів мобільного застосунку"

### 1. Мета роботи
Трансформація статичного користувацького інтерфейсу у функціональний застосунок шляхом імплементації локального збереження даних, управління станом за допомогою `StatefulWidget`, реалізації механізмів валідації та розділення кодової бази на архітектурні шари (UI, Business Logic, Data/Repository).

---

### 2. Завдання до лабораторної роботи

**Мета завдання:** Наповнити розроблені екрани (з Лаб. №2) бізнес-логікою. Реалізувати флоу авторизації (реєстрація, логін) з використанням локального сховища та базові CRUD-операції (Create, Read, Update, Delete) для сутностей на головному екрані.

**Функціональні вимоги:**
1. **Реєстрація (Sign Up):** Реалізувати запис даних нового користувача у локальне сховище.
2. **Валідація даних:** Вхідні дані форми реєстрації та авторизації повинні проходити жорстку перевірку перед збереженням.
   - *Приклад:* Електронна пошта повинна містити `@` та домен; пароль — мінімум 8 символів; ім'я — не містити цифр. Будь-які порушення мають блокувати операцію та виводити користувачу чіткі повідомлення про помилку на UI.
3. **Авторизація (Sign In):** Реалізувати звірку введених даних (логін/пароль) із збереженими у локальному сховищі. 
   - *Success:* Навігація на головний екран.
   - *Fail:* Блокування переходу та вивід повідомлення про помилку.
4. **Управління даними (CRUD) на головному екрані:**
   - Користувач повинен мати змогу створювати, читати, редагувати та видаляти дані (модифікація стану), що стосуються бізнес-ідеї вашого застосунку.
   - Дані профілю авторизованого користувача мають відображатися на відповідному екрані (Profile Screen) або в елементах навігації (наприклад, AppBar/Drawer).

**Критерії приймання (Acceptance Criteria) та архітектурні обмеження:**
- **Принцип інверсії залежностей (Dependency Inversion):** Пряма залежність UI від конкретної реалізації бази даних **категорично заборонена**. Класи для роботи з локальним сховищем повинні базуватися на абстракціях (абстрактні класи / інтерфейси в Dart). Це гарантує можливість безболісної міграції з локального сховища на REST API у майбутньому.
- **Розподіл на шари (Separation of Concerns):** Код не повинен бути звалений у "God Classes" на 1000+ рядків. Вимагається чіткий поділ на директорії/шари:
  - `features/` (або `ui/`) — екрани та віджети.
  - `domain/` (або `logic/`) — абстракції та бізнес-правила.
  - `data/` (або `repositories/`) — імплементація роботи зі сховищем.
- **Тотальна незмінність (Immutability):** Максимальне використання модифікаторів `final` та `const`. Дані, які не мутують протягом життєвого циклу об'єкта, повинні бути жорстко зафіксовані.
- **Управління станом:** На даному етапі зміна та оперування даними на UI здійснюється виключно за допомогою механізмів `StatefulWidget` (`setState`).

### 3. Порядок виконання

#### 3.1. Синхронізація репозиторію
1. Успішний захист Лабораторної роботи №2 є жорстким блокером.
2. Переконатися, що гілка з Лаб. №2 успішно змерджена у `main` (або `master`).
3. Створити нову гілку (наприклад, `feature/lab-3-logic`) від актуального стану `main`.

#### 3.2. Вибір та імплементація сховища
1. Обрати технологію локального збереження даних (наприклад, `shared_preferences`, `sqflite`, `hive` або `flutter_secure_storage`).
2. Створити абстрактний клас контракту репозиторію (наприклад, `IAuthRepository`).
3. Написати конкретну імплементацію цього контракту з використанням обраного пакету.

#### 3.3. Інтеграція логіки з UI
1. Підключити репозиторії до `StatefulWidget`-ів.
2. Реалізувати асинхронні виклики (`Future`, `async/await`) для роботи з даними, показуючи індикатори завантаження (`CircularProgressIndicator`) під час виконання операцій.

### 6. Вимоги до захисту (Контрольні питання)

Для успішного захисту студент повинен продемонструвати глибоке розуміння наступних тем:
1. **Асинхронне програмування:** Що таке `Future`, `Stream`, `async`, `await`? Як уникнути блокування основного потоку (UI thread)?
2. **Локальні сховища:** Пояснити різницю між Key-Value сховищами (SharedPreferences) та реляційними БД (SQLite). Коли доцільно використовувати кожне з них?
3. **Екосистема:** У чому концептуальна різниця між пакетами (Packages) та плагінами (Plugins) у Flutter?
4. **Архітектура:** Для чого потрібні абстрактні класи? Продемонструвати на своєму коді, як легко замінити локальну БД на зовнішнє API.
5. **Research (Підготовка до наступної лаби):** Знати базову концепцію патерну Dependency Injection та ознайомитись із сутністю `Provider`.
